# Backup and restore

JETT exports documents, records, reading positions, arrived moments, organization spaces, space feeds, user-facing settings, the durable outbound queue and the device delivery-evidence log as one encrypted JSON envelope. The user supplies and confirms a passphrase of at least 12 characters. Web Crypto derives a 256-bit AES-GCM key with PBKDF2-SHA-256, a random 16-byte salt and 310,000 iterations, then encrypts with a random 12-byte IV. The passphrase is neither serialized nor stored by JETT and cannot be recovered by the application.

Settings offers a staged restore: choosing an encrypted file asks for its passphrase, authenticated decryption and structural validation complete before document, record and arrival counts appear, and no device data changes during that inspection. A separate **restore this backup** action replaces the five application IndexedDB collections in one transaction, restores settings and organization data, then reloads from persistence. Queued sends and delivery evidence are restored only when the export's device identity matches the current device. Legacy plaintext `jt-export` files remain importable for migration, with an explicit warning to make the next backup encrypted; new downloads use only the encrypted envelope.

The validator rejects malformed JSON, foreign formats, missing collections, duplicate document IDs, records without their documents, reading positions without their documents, invalid settings and organization records that fail the existing organization schemas. Application data, the transport outbox and the append-only delivery log live in separate IndexedDB databases, so the browser cannot commit them in one native transaction. Before staging, JETT requires contiguous log sequence numbers and recomputes every full-moment SHA-256 hash. The restore coordinator applies an eligible same-device outbox and log before the five-store application transaction and compensates local settings, organization data, the prior outbox and the prior log if that transaction fails. If compensation itself fails, the product reports that recovery is incomplete instead of claiming the previous state was preserved.

`test/backup.test.mjs` covers encryption round-trip, absence of plaintext and passphrase from the envelope, security-parameter validation, wrong-passphrase failure and authenticated tamper rejection, log migration and log-hash rejection. `test/restore-coordinator.test.mjs` injects application-commit and compensation failures to prove successful rollback and honest partial-recovery reporting. `test/sync-log.test.mjs` proves delivery-log replacement is atomic and device-scoped. The desktop production-browser journey verifies passphrase confirmation, exports populated data through the encrypted boundary, proves a wrong passphrase cannot enable restore, unlocks with the correct passphrase, stages the file, restores it, waits through reload and compares restored document, record, arrival and same-device outbox IDs with the source export.

## Current boundary

The encrypted export does not contain pairing credentials. Queued sends and delivery evidence carry device-bound transport identity, so JETT refuses to replay another device's queue or install its log while still restoring portable saved data. Encryption protects a backup when it is copied or stored; it does not protect data while the application is open, escrow a lost passphrase, schedule backups, prove external backup custody or replace physical-device restore testing. This slice proves encrypted saved application-data, same-device outbox recovery and hash-verified same-device delivery-log recovery; it is not yet a complete device migration or physical-device restore.
